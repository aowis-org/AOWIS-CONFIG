## What the project is

- Repository: **AOWIS-CONFIG**, an independent Apache-2.0 C++20 library
  *planned* for common persistent-configuration machinery.
- Component ownership: each application/service has its own storage root
  within `aowis/<owner>`; there is **no universal mutable `shared/` root**.
- Code reuse: include/configure it as a pinned submodule only in components
  that own persistent settings. Non-owning libraries receive typed settings.
- Runtime: AOWIS-NETWORK owns WireGuard sockets/tunnels/status. CONFIG stores
  configurations only. DVMDB repositories and working-copy data are separate.
- Compatibility: **no productive installations yet**. Breaking removal of
  legacy experimental stores is expressly accepted and preferred.

## Downstream context: AOWIS-GUI

At the design-discussion checkpoint, the GUI has an experimental
**Settings → WireGuard VPN** page with list, import/edit/delete UI, syntax
highlighting, `Used by` and `Status` views. Native profile persistence is not
yet connected: the GUI initially holds profiles in memory. Existing remote
DVMDB settings still have `wireguard_profile_path`, pointing to an external
`.conf` file. A later GUI integration must remove that field in favor of a
stable WireGuard profile ID and use CONFIG as the authoritative persistence
layer. Runtime indicators must come from AOWIS-NETWORK, not static metadata.
WASM entry is disabled with an explanatory tooltip by design.

The old GUI INI example had `[servers] profiles` as escaped JSON, `[units]
custom_profiles` as a Qt-encoded JSON/byte array, and ordinary `[map_server]`
settings alongside API credentials. All require consolidation in separate
later phases. **Do not add yet another GUI-only persistence engine.**

## Essential acceptance scenarios

1. Import `.conf`, edit, close application, relaunch: complete original text
   still exists and has no external path dependency.
2. Copy the owner's entire config root to a new user/machine: profile objects
   and ID references are intact; external endpoints and platform limitations
   are diagnosed rather than hidden.
3. Two DVMDB/map/other configured service connections reference the same
   profile; `Used by` shows the configured count, without duplicating secrets.
4. Delete/rename behavior follows stable IDs and reference guards; user sees
   conflicts instead of silently losing data.
5. Private keys are never logged; stored files and directories receive
   appropriate protection; interrupted writes cannot silently corrupt or
   erase the previous committed version.
6. Two instances of the same owner accessing the same root have defined
   conflict behavior. Different app owners cannot collide by default.
7. No Qt dependency is needed to build the C++ core; WebAssembly does not
   expose embedded WireGuard functionality.
